# Banking App

A layered banking demo that combines database design and object-oriented C++:
PostgreSQL database, C++ backend with a class hierarchy and a small REST API, and an HTML/CSS/JS frontend.

## What it does (showcase mode)

No login. The app opens as an already-enrolled customer and shows:

| Feature | Status |
|---|---|
| Balance, account holder, fake IBAN | Live from the database |
| Transaction history | Live from the database |
| Transfer to another account (by IBAN) | Live, updates both balances |
| Installment / split-pay plans (3-12 payments) | Live, due dates tracked, charged automatically |
| Card type, spending limit | Display-only |
| Change limit, card settings, edit profile, log in, enroll | Visible but disabled (future work) |

The account switcher in the header only exists so the demo can show transfers between customers.

## Architecture

```
Dataset (CSV) -> PostgreSQL (staging table -> real tables)
                      |
        C++ backend: Database layer (libpqxx)
                      |
        Domain classes: Account, Transaction -> Transfer, InstallmentPayment
                      |
        REST API (cpp-httplib) also serves the frontend
                      |
        Frontend (HTML/CSS/JS, fetch())
```

### Class hierarchy

```
Account                       holds balance; credit() / debit() throw on bad input
Transaction (abstract)        amount; pure virtual apply(Account&), type()
 |- Transfer                  debit source, credit destination
 '- InstallmentPayment        debit account, remembers its plan id
```

`apply()` is virtual, so code can handle any transaction type the same way.
Exceptions: `InvalidAmount` (amount <= 0) and `InsufficientBalance` (carries the current balance in its message).

### Database (normalized, one-to-many chain)

```
customers 1--* accounts 1--* transactions
                  accounts 1--* installment_plans 1--* installment_payments
```

- One `transactions` table with a `type` column (`transfer`, `installment`) instead of one table per type.
- Amounts are signed in `transactions` (negative = money out) so history is simple to display.
- `id` and `created_at` are generated by PostgreSQL, not by C++.
- Transfers and installment charges run inside one database transaction, so balance and log never disagree.

### Installments without a scheduler

Creating a plan inserts N payment rows with real due dates (30 days apart, the first one today).
Every time account data is requested, the backend charges any payment whose due date has passed.
If the balance is too low the payment stays pending and is retried on the next read.
The "Simulate +30 days" button shifts pending due dates earlier so the effect can be shown in a demo.

### Design decisions

- No standalone deposit/withdrawal: a real online bank does not let customers create money, and cash withdrawal is an ATM action. Incoming money would be a transfer from another account.
- "Current customer" is a single variable in `frontend/script.js`, and the API is scoped by account id, so login can be added later without touching the domain classes.

## API

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/accounts` | list accounts |
| GET | `/api/accounts/{id}` | account details (also charges due installments) |
| GET | `/api/accounts/{id}/transactions` | history, newest first |
| GET | `/api/accounts/{id}/installments` | plans with payments |
| POST | `/api/transfer` | `from_id`, `to_account_number`, `amount` |
| POST | `/api/installments` | `account_id`, `total`, `installments` |
| POST | `/api/demo/advance` | `days` (demo only) |

Errors come back as `{"error": "..."}` with status 400.

## Project layout

```
docker-compose.yml        PostgreSQL 17
sql/schema.sql            all tables
sql/migrate.sql           adds columns / fake IBANs / card fields to an existing database
backend/include/          Account.h, Transaction.h, Transfer.h, InstallmentPayment.h, Database.h, httplib.h
backend/src/              main.cpp (routes), Database.cpp (all SQL)
backend/test/             account_test.cpp (no database), db_connection_test.cpp
frontend/                 index.html, style.css, script.js
```

## Run it (macOS)

1. Database
   ```bash
   docker compose up -d
   ```
   Run `sql/schema.sql` in DBeaver, load the customer CSV into `raw_customers`, then
   `INSERT INTO customers ... SELECT ... FROM raw_customers;` and `INSERT INTO accounts (customer_id, balance) SELECT id, 1000 FROM customers;`.
   Then run `sql/migrate.sql` once.

2. Build and start the server (from `backend/`)
   ```bash
   brew install libpqxx libpq
   cd backend
   g++ -std=c++20 -Iinclude -I/opt/homebrew/include -I/opt/homebrew/opt/libpq/include \
       -L/opt/homebrew/lib -L/opt/homebrew/opt/libpq/lib \
       src/main.cpp src/Database.cpp -lpqxx -lpq -o bank_server
   ./bank_server
   ```
   Connection defaults to `host=localhost port=5432 dbname=bankingdb user=admin password=admin123`.
   Override with `DB_CONN="host=... dbname=... user=... password=..." ./bank_server`.

3. Open http://localhost:8080

Class-only test (no database): `g++ -std=c++20 -Iinclude test/account_test.cpp -o account_test && ./account_test`
